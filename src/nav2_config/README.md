# nav2_config

**Layer:** 5 (navigation). **Status:** SCAFFOLD (runs on the stub stack; untested on the real gait or hardware).
**Replaces:** `nav_stub` when launched with `navigation:=external`.
**Action server:** `navigate_to_pose` (served by Nav2's `bt_navigator`, same name and type as the stub).
**Publishes:** `/cmd_vel_nav` (from Nav2's `velocity_smoother`), **the only publisher**; `cmd_vel_mux` forwards it to `/cmd_vel`.

## What this does

`launch/nav2.launch.py` starts Nav2's navigation servers with the velocity chain
re-routed so Nav2 never publishes `/cmd_vel`:

```
controller_server --cmd_vel_raw--> velocity_smoother --/cmd_vel_nav--> cmd_vel_mux --> /cmd_vel
behavior_server  --cmd_vel_raw--^        (recovery moves: spin, backup, wait)
```

Nav2's stock `navigation_launch.py` ends the chain at `/cmd_vel`, which would
bypass `cmd_vel_mux` (no teleop override, no watchdog) and break the one-publisher
rule. `cmd_vel_raw` is internal and not part of the contract.

```bash
ros2 launch bringup full_stack.launch.py sim:=false navigation:=nav2   # whole stack, Nav2 instead of nav_stub
# or the two-step form (e.g. with your own map server):
ros2 launch bringup full_stack.launch.py sim:=false navigation:=external
ros2 launch nav2_config nav2.launch.py
```

`navigation:=nav2` runs Nav2 on `slam_stub`'s empty map; the obstacle tests below use the two-step form so
a fake map with obstacles can be served instead.

## Testing obstacle avoidance

One command from the repo root (Docker running, image built with `./docker/build.sh`):

```bash
tools/run_nav2_avoidance.sh                      # every default scenario
tools/run_nav2_avoidance.sh zigzag obstacle_1@90 # chosen ones; <map>@<degrees> also checks the goal heading
```

Each scenario runs in its own fresh container: the stub stack with `slam:=external`,
`test_map.launch.py` serving a fake map (with the `map -> odom` identity transform that
`slam_stub` would normally provide), Nav2, then `avoidance_test.py`, which sends a goal and
checks the outcome. Output goes to `reports/nav2_avoidance/` (git-ignored): `report.html`
(open it in a browser for a replay of every run), `run_<scenario>.json`, and `logs/` for a
failed one. Exits non-zero if any scenario fails.

| Scenario | Layout | Passes when |
|---|---|---|
| `obstacle_1` / `_2` / `_3` | 1, 2 or 3 boxes side by side across the straight line to (4, 0) | goal reached, never within 0.30 m of an obstacle, path bent around it |
| `zigzag` | three full-width walls with a 1.2 m gap each, alternating high, low, high: no way around; goal (4.5, 0) | same |
| `unreachable` | goal (4, 0) inside a closed box: no path exists | Nav2 reports `ABORTED` (no hang, wandered less than 0.6 m) |
| `obstacle_1@90`, `@180` | as `obstacle_1`, but the goal also asks for that final heading | same, and final heading within 0.5 rad of it |

That test only checks that failure is reported: stock Nav2 spins and backs up for about 25 s
before it aborts, and nothing shortens that yet (see "Unreachable goals are slow to fail" below).

The heading check uses Nav2's own `yaw_goal_tolerance` (0.5 rad, about 29 degrees), and the robot
stops as soon as it is inside it (the runs end 26-27 degrees off), so the test shows the heading
is honored to that tolerance, not precisely. Tighten `yaw_goal_tolerance` in `config/nav2_params.yaml`
(and `--yaw-tol`) for a stricter result.

Maps are generated by `scripts/make_test_maps.py`. The test uses a fake map with the
obstacles known in advance; it does not test sensing (nothing publishes a scan yet).

**Unreachable goals are slow to fail (open, not done anywhere).** Giving up at once when no path
exists was meant to be handled by the behavior tree, but it is not: the tree treats a Nav2 `ABORTED`
like any other failure and tries the skill 3 times, and stock Nav2 spins and backs up for about 25 s
before each abort, so an unreachable goal takes roughly 75 s or more to become `FAILED`. With an LLM
key the planner then replans once and may send the robot to the same place again (about as long
again). The tree's per-attempt limit is also a fixed 60 s whatever the distance, while Nav2 is capped
at 0.3 m/s, so a goal more than about 18 m of path away times out even when it is reachable. Possible
fixes, none started: a Nav2 behavior tree XML without the recovery branch for "no valid path", telling
`ABORTED` causes apart in the tree (Humble's `NavigateToPose` result carries no error code), and a
timeout derived from the path length.

Depends on other teams or hardware:
- **Obstacle sensing.** The costmaps use only the static map. Nothing publishes a scan or point cloud, so
  Nav2 cannot avoid anything it was not told about.
- **Real map and localization** (`slam`, `state_estimation` are stubs).
- **The real gait.** Values marked `[tune]` in `config/nav2_params.yaml` (speeds, accelerations, 0.30 m
  radius) are guesses until locomotion says what the legs can follow.
- Only ever run against the stub stack (`sim:=false`), never on MuJoCo or hardware.
