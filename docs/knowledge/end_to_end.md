# The Full Stack, Command to Motor — The Whole Rant

Okay so a human wants the robot to do something, and somewhere at the far end a motor has to spin with exactly the right current. This is the story of everything in between — how a spoken goal or a joystick nudge travels all the way down through planning, decision-making, control, and hardware until electricity moves a joint. I'm going to walk it top to bottom, and the through-line to hold onto is that each layer runs slower and thinks more abstractly than the one below it: the top reasons in words a few times a second, the bottom switches transistors thirty thousand times a second, and every layer's job is to translate the layer above into something the layer below can act on.

## The fork at the very top

The first thing that happens depends entirely on how the human is commanding the robot, and there are two completely different paths that don't rejoin until near the bottom.

In teleoperation, a human is driving directly with a joystick or keyboard, and the crucial insight is that the human is the planner. There's nothing to decompose, nothing to reason about — the person is watching the robot and closing the loop with their own eyes and hands in real time. So the command skips almost the entire stack and goes nearly straight to the locomotion policy.

In autonomous operation, the human gives a goal in plain language — "bring me the cube from the table" — and now the whole high-level stack has to fire to turn that vague sentence into concrete, coordinated robot behavior. This is the interesting path, and most of the top of the stack exists to serve it.

They diverge immediately and hard. Let me walk each.

## The teleop path — the short one

Keyboard or joystick input gets read by an existing ROS package you don't even write — teleop_twist_keyboard or teleop_twist_joy. It publishes a velocity command to a topic called /cmd_vel: three numbers, vx, vy, vyaw, in the robot's body frame. The locomotion policy subscribes to /cmd_vel and folds those three numbers into its observation. That's the whole path — human, to /cmd_vel, to policy, to motion. No planner, no behavior tree, no language model. You use this for testing, demos, and collecting data, and it's worth knowing it exists because it's the fallback that always works when the fancy autonomy is broken.

One subtlety to carry forward: those velocities are in body frame. vx means "forward from wherever the robot is currently facing," not "north." That distinction barely matters here but becomes important in the autonomous path, where the command is born in world frame and has to get rotated into body frame before the policy can use it.

## The autonomous path — the full high-level stack

Now the real thing. It flows: input becomes a string, a task planner reasons once to produce a plan, a behavior tree executes that plan reactively, and navigation skills get bridged down to the same /cmd_vel the joystick would have produced. Four stages.

Input becomes a string. Voice goes through Whisper — speech-to-text, runs locally, a few hundred milliseconds — and comes out as text. Typed text skips Whisper. Either way you land on a string representing the human's goal, published to a topic, and that string wakes up the task planner.

The task planner reasons once. This is the slow, deliberate "what should I do" layer, and the important thing about it is that it runs once per goal and then goes back to sleep — it's not a loop. Its job is to turn the goal string into an ordered list of skills. To do that it needs three things. First, a skill library — a YAML file you wrote once that defines every capability the robot has, each skill annotated with its preconditions (what must be true to start it) and postconditions (what will be true when it finishes). The planner can only use skills that exist here, which stops the language model from inventing capabilities the robot doesn't have. Second, the current world state — assembled right now from live topics: where the robot is (from the state estimator), where objects are (from perception), gripper state, battery. Third, the language-model call itself, which takes the goal plus the world state plus the skill library and emits a JSON list of skill calls. You validate that JSON — are all the skills real, do the preconditions chain correctly from one step to the next — retry if it's malformed, and publish the result. For "bring me the cube" it comes out as something like navigate_to(table) → pick(cube) → navigate_to(user) → place(). An ordered sequence. Then the planner sleeps until a new goal arrives or something fails badly enough to demand a replan.

The behavior tree executes it. This is the fast, always-running layer that actually makes the plan happen in the messy real world, and it's where the real orchestration lives. It ticks at 20Hz — the entire tree gets evaluated twenty times a second from the root down, every node reporting SUCCESS, FAILURE, or RUNNING. A few mechanisms make it work. The ReactiveSequence pattern puts safety guards at the top — is the battery okay, is the robot upright, are there faults — and re-checks them every single tick, so if something goes wrong mid-action the tree can abort within one tick rather than blindly finishing a doomed motion; that constant re-checking is what makes it "reactive" instead of just a script. The blackboard is shared memory that ROS subscribers keep continuously fresh — robot pose streaming in at 500Hz, object poses at 30Hz, gripper state, battery — so condition nodes can read the current state of the world in microseconds without making slow calls. The action nodes are the long-running skills, each one a client to a ROS action server that runs asynchronously, reports feedback along the way, and can be cancelled on abort; when the tree ticks "navigate to table," it fires a goal at an action server and gets RUNNING back while the work happens. And recovery wraps each skill: if it fails, a recovery routine runs — clear the costmap and retry for navigation, re-detect the object and retry for grasping — and only after retries are exhausted does the failure bubble up to the planner for a full replan.

Nav2 bridges high-level down to locomotion. Here's the seam between the whole high-level world and everything below it. When the behavior tree's active skill is "navigate to the table," it's really invoking Nav2, the navigation stack. Inside Nav2, a global planner runs about once a second and finds a path through a costmap built from the SLAM map, and a local controller runs about twenty times a second and turns that path into an actual velocity command. And what does the local controller output? /cmd_vel — the exact same three numbers, vx, vy, vyaw, that the joystick produced in the teleop path. The locomotion policy subscribes to /cmd_vel and has no idea whether a human's thumb or Nav2's path-follower put those numbers there. That's the elegance of the whole design: teleop and autonomous are utterly different above /cmd_vel and completely identical below it. Nav2 is the piece that lets the behavior tree drive the robot without knowing anything about legs or gaits — it just emits velocities, and the policy handles the rest. High-level's job ends the moment it produces /cmd_vel.

## The handoff into the body — from command to torque

Now we cross from "what to do" into "physically do it." The locomotion policy takes /cmd_vel plus its observation and outputs joint position targets — a desired angle for each of the twenty-five or twenty-nine joints. But here's the pivot that defines the entire bottom half of the stack: a motor doesn't consume angles. It consumes electric current, which produces torque. So everything from here down exists to answer one question — how do I turn a desired joint angle into exactly the right current in exactly the right winding, reliably, thousands of times a second? Each stage below is one step of that translation, and each runs faster than the one above.

First, angle becomes torque. The desired joint angle has to become a desired torque. In a full system the whole-body controller does this while simultaneously juggling balance and foot contacts — we're black-boxing its internal optimization, but its output is a torque per joint. In a simpler v0 you skip the WBC entirely and use a plain PD controller: torque equals a stiffness gain times the position error plus a damping gain times the velocity error. Either way, this stage runs around 500Hz to 1kHz and its output is a torque command, in newton-meters, for every joint.

## ros2_control — the real-time spine

Those torque commands now enter ros2_control, the standardized framework ROS provides for talking to hardware, and the mental model to hold is that it draws a clean line between controllers (code that computes commands) and hardware (the physical robot), with the two sides talking through standardized interfaces — command interfaces for things you write down to hardware (target torque) and state interfaces for things you read up from hardware (actual position, velocity, torque).

The engine is the controller manager, running a tight real-time loop at 1kHz. Every single millisecond it does three things in strict order: read the current state up from hardware, update the active controllers so they compute fresh commands, and write those commands back down to hardware. Read, update, write, a thousand times a second.

You configure two things here, and this is where YAML enters your life. Inside the robot's URDF you add a <ros2_control> block that declares, per joint, which command interfaces it exposes (effort/torque) and which state interfaces it reports (position, velocity, effort) — this is what maps the human-readable name "left_hip_pitch" onto a hardware entity the framework can actually command, and it's mostly copy-and-rename per joint. Separately, a controllers YAML declares which controllers are active, their 1kHz update rate, and their per-joint gains — high stiffness on knees, low on wrists — which you tune by hand.

And here's the point people trip on: ros2_control itself has no idea how to speak EtherCAT or CAN. It only knows "read state, write command" through a plugin. That plugin is the EtherCAT driver — it isn't a separate downstream node, it's the hardware interface that ros2_control loads and whose read() and write() functions it calls directly inside that 1kHz loop. Keep that straight and the rest clicks.

## Onto the wire — EtherCAT and PDOs

The ethercat_driver_ros2 plugin takes the torque command ros2_control wants to write, packs it into an EtherCAT frame, sends it down the physical cable, and reads the response back. To get why that's fast enough, you need what EtherCAT actually is.

EtherCAT is a real-time industrial network, and physically it's a single cable that daisy-chains through every motor drive — out from the computer, through drive one, drive two, all the way to drive N, and back. One frame travels the whole loop. The clever part: each drive reads its slice of the frame and writes its response as the frame passes through it in hardware, in about three hundred nanoseconds, with no processor involved. So one frame per millisecond services every drive, and the round trip for twenty-five drives comes in under a hundred microseconds — comfortably inside the 1kHz budget.

The data each cycle is organized into PDOs, Process Data Objects, in two directions. The RxPDO is received by the drive — what you're commanding: a control word (enable, fault-reset) and the target torque. The TxPDO is transmitted by the drive — what it reports back: a status word plus actual position, velocity, and torque. And the standard that makes all of this interoperable is CiA 402, the common language of servo drives. It fixes the addresses of everything — target torque lives at 0x6071, actual position at 0x6064, control word at 0x6040, status word at 0x6041 — and defines a standard state machine each drive walks through to go from powered-but-disabled to operational. Because it's standardized, any compliant drive speaks the same dialect, and your job shrinks to telling the driver which addresses map to which quantities for your specific motors.

## The mapping YAML, filled from datasheets

This is the concrete, tedious, one-time work. You write a slave-configuration YAML that tells the driver, for each drive on the chain, how to build its PDOs. For each slave you specify its vendor ID and product ID — unique model identifiers you pull from the drive's datasheet or its ESI file, the XML description the manufacturer ships — which tell the master what kind of device it's talking to. Then the RxPDO mapping: which CiA 402 objects go in the outgoing packet, typically control word and target torque, each entry needing the object's index, sub-index, and bit size, all listed in the datasheet's object dictionary. Then the TxPDO mapping: which objects come back — status word, actual position, actual velocity, actual torque — same index/sub-index/size, from the same datasheet. Plus the distributed-clock settings, usually a 1ms cycle.

So the actual workflow when a new actuator arrives: open its datasheet or ESI file, find the object dictionary, look up the index and size of each quantity you care about, and transcribe those into the YAML. It's careful copying, not cleverness — but get a single index or bit-size wrong and that drive receives garbage and either sits dead or faults, and this is the number-one source of first-time EtherCAT pain. That mapping table exists precisely because the driver needs to know exactly where in each drive's memory the torque command goes and the position reading comes from, and only the datasheet knows that.

One more configured thing lives here: distributed clocks. Every drive has its own clock crystal and they drift apart. Distributed clocks is the mechanism where the master measures the propagation delay to each slave and continuously nudges them so all drives execute their control at the same instant, synchronized to under a microsecond. Without it some joints would lag others by hundreds of microseconds, and the whole-body controller's assumption that every joint moves together would quietly break.

## Inside the drive — FOC and the closing of the loop

The frame reaches a drive carrying a target torque. Inside each drive is a small microcontroller running field-oriented control at twenty to thirty kilohertz — far faster than anything above it — whose entire job is to produce exactly the commanded torque by controlling the currents in the motor's three phases. The shape of it, with the deep math black-boxed: it measures the phase currents, transforms them into a reference frame that rotates with the rotor, runs PI controllers to drive the torque-producing current component to its target (the target current is just the commanded torque divided by the motor's torque constant, a number from the datasheet), and transforms back into the PWM voltages that switch the transistors feeding the windings. The sign of the torque command sets the direction — positive spins one way, negative the other.

And crucially, the encoder on the motor reads the actual joint angle every cycle, and that reading flows all the way back up: encoder to TxPDO, into the EtherCAT frame, back through the driver into ros2_control's state interfaces, into the state estimator, and into the policy's very next observation. The loop closes. The policy asked for an angle, the whole chain drove the motor toward it, and the measured result comes straight back up to shape the next command. That returning stream is the same data the state estimator fuses to produce the base pose and joint state the policy observes — which is exactly where the low-level flow feeds back into the mid-level one.

## The CAN and MCU branch

Everything so far assumed native EtherCAT drives — plug them on the chain, they speak EtherCAT and CiA 402 directly, and there's no firmware to write, just YAML mapping. But many affordable actuators — Unitree's, T-Motor's, ODrive-style — speak CAN instead, a simpler and slower automotive bus. You can't daisy-chain those onto the EtherCAT cable, so you need a bridge, and that's where a microcontroller comes in.

The MCU sits between the two worlds and translates. On one side it's an EtherCAT slave — to ros2_control and the EtherCAT master it looks like just another drive on the chain, receiving RxPDO torque commands and reporting TxPDO state. On the other side it's a CAN master — it takes those torque commands and re-transmits them as CAN messages to the actual motors, reads the motors' CAN replies, and folds them back into its TxPDO. So it runs firmware, embedded C, that every cycle reads the incoming EtherCAT command, sends it out over CAN, reads the CAN responses, and writes them back to EtherCAT — a real-time protocol translator. This is exactly the kind of firmware a low-level team writes, and it's why a bridge board is typically an EtherCAT slave controller chip plus a CAN transceiver plus an MCU. So your two possible topologies are: native EtherCAT, drives straight on the chain, no MCU, just mapping YAML; or an EtherCAT-to-CAN bridge, where an MCU impersonates an EtherCAT slave while translating to CAN for the motors and requires real firmware. Which one you have comes down entirely to what actuators you bought.

## The whole thing in one breath

A human either grabs a joystick — in which case they are the planner and their command flows straight to /cmd_vel — or speaks a goal, which Whisper turns to text, which wakes a task planner that reasons once, combining a skill library and live world state through a language model into an ordered skill sequence, which a behavior tree then executes reactively at 20Hz, guarding safety every tick, reading the world from a blackboard, calling action servers for each skill, and recovering from failures — and when a skill is navigation, Nav2 turns it into a path and then into /cmd_vel, the very same three velocity numbers the joystick would have produced, so both paths converge there. The locomotion policy takes /cmd_vel and outputs joint angle targets; a WBC or a PD controller turns those into torques; ros2_control's 1kHz read-update-write loop takes those torques and, through its EtherCAT hardware plugin, packs each into a CiA 402 target-torque object at address 0x6071 and fires one EtherCAT frame down a daisy chain that services every drive in under a hundred microseconds, its packet layout defined by a YAML mapping you filled from each actuator's datasheet, all drives clock-synchronized to under a microsecond; inside each drive, field-oriented control at thirty kilohertz turns that torque into phase currents that spin the motor, while the encoder reads the actual angle and sends it back up through EtherCAT into ros2_control into the state estimator into the policy's next observation, closing the loop — and if the motors speak CAN instead of EtherCAT, an MCU running your firmware sits in the chain wearing an EtherCAT-slave mask on one face and a CAN-master face on the other, translating between them every millisecond. From a sentence to a spinning motor, that's the whole stack.
